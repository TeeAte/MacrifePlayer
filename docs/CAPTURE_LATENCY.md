## 采集静止文字稳定与近期延迟估计（2026-11-17，仅离线验证）

用户明确只有静止文字闪烁。本轮没有连接或启动采集卡，使用此前保留的16张1080p NV12真实游戏采集帧，以及新建NV12/YUVS测试画面验证。

- 采集设置新增默认开启的「静止文字稳定」。几何文字检测在后台最多每秒一次，不运行OCR识别模型，也不等待检测结果；没有识别到文字时直接保留模型输出。
- 只在检测到的文字框中，检查相邻源帧的细笔画位置、对比度及色彩是否稳定。按笔画对比度加权的区域稳定性门限拒绝移动文字；通过后仅处理笔画及最多3像素邻域。源帧对象与像素不被改写，文字框之外的中间帧像素逐字节保留。
- 这是局部文字处理。此前影响运动效果的全画面源图重建仍处于撤回状态；本轮用真实移动物体中间位置、移动文字绕过、区域外像素完全不变等独立断言防止该问题回归。
- Apple / MetalFX 将文字处理编码进已有 GPU 批次，不增加帧队列或一次额外 GPU 同步。CoreML / RifeMetal 使用每个worker独立的暂存槽。纹理缓存定期清理，检测结果在配置切换后失效。支持8位NV12/YUVS；不支持的格式保留原模型结果。
- 修正 CoreML 输入色度零点、BT.709/601/2020 与全/视频范围往返转换的一致性，避免静止彩色文字往返后改变颜色或亮度。
- CoreML 源尺寸光流上采样、warp、mask与融合合并，保留FP16中间量量化语义；1080p参考GPU测试约1.34ms→0.78ms，每实例减少43.5MiB源尺寸临时缓冲。与参考计算的平均RGB误差约0.000066、最大约0.00195，已覆盖非整数缩放、边界越界光流与色彩往返。
- 采集播放时钟改用最近7次有效推理耗时的中位数，而非包含冷启动编译峰值的累计平均。RifeMetal 额外文字阶段的成本也计入播放预算。未增加采集缓冲；CoreML保持全计算单元、双实例。

## 视频文件吞吐与预缓冲优化（2026-11-17）

桌面样本 `aespa - Whiplash.mp4` 实际为 H.264、4096×2304、24FPS，带 AAC 音轨。本轮按用户要求测试 Apple VideoToolbox、CoreML RIFE 和 MetalFX 的 1080p 推理，目标为 2X / 48FPS；不改变 RifeMetal Fast 的实现。

- 文件解码、模型处理和显示分开；新增 4 帧有界解码预读队列。源帧带来源代际，跳转时清空旧队列并等待处理门闸，防止旧画面进入新时间轴。
- 视频设置新增 0.5 / 1 / 2 / 4 秒预缓冲，以及 256MB / 512MB / 1GB / 2GB 帧缓存预算，默认 2 秒 / 1GB。容量按源分辨率保守估算，并留显示余量；实际缓冲时长受内存上限限制，模型及其工作区另计。
- 补帧首批结果未就绪时，音频限流器不再提前播放。缓存不足时同步暂停音频和视频时钟，生产线程继续工作；回填后同步恢复。短片尾帧不足阈值时直接播放，片尾看门狗在预计算/回填期间停用。
- CoreML 文件任务每 4 对连续帧分配给同一 worker，提高前帧转换/特征复用；保留双实例。文件等待真实模型预热，不先生成大量兜底结果占满缓存。固定目标帧率分支只输出时间网格，避免额外输出全部源帧；静止画面跳过也对时间网格生效。
- Apple / MetalFX 文件中间帧直接缓存模型输出尺寸，在显示时缩放一次，省去先放大到源 4K 尺寸的中间缓冲；保留源帧原始像素与真实 AI 中间帧。采集默认仍返回原尺寸生成帧。
- 没有新画面时减少重复 GPU 渲染；字幕动画/清除继续更新。文件显示采用有界 3 帧 GPU 在途，显示时钟按屏幕刷新率取帧。档位切换清空旧帧率缓存并保留已加载模型。
- 依用户要求，CoreML 固定 `MLComputeUnits.all`，移除 CPU-only/GPU-only/混合调试覆盖与手动单实例覆盖；文件解码显式配置全部活动逻辑核。系统模型和硬件解码仍由系统管理执行资源，配置不等于强制所有设备维持 100% 占用。

实测记录保存于 `output/file-buffer-20261117/`。此前音频抢跑时，20 秒短测中 Apple/CoreML/MetalFX 分别丢弃 132/71/255 帧；缓冲后的对应 30 秒短测均为 0 丢帧，音画偏差约 27/34/9ms。缓存回填会暂停播放，这些数据不能解释为持续达到 48FPS。

硬件限制仍然存在：Apple 1080p 每对约 95–100ms，MetalFX 约 44ms；CoreML 1080p 双实例也低于每秒24对的需求。因此本机上仍可能发生回填等待。单实例、CoreML 混合计算、Apple 系统完成回调及另一缩放路径未显示吞吐优势，未作为默认执行策略。缓存用于吸收波动，不宣称提高模型的持续算力，也未自动降低用户选择的推理精度。

## 实现

- 采集回调只收帧、解析元数据，并在手动主机30模式下按PTS网格固定隔帧取样，再投递到有界队列；转换与推理在独立线程执行。
- 极限模式：采集待处理和 AI 输入各最多 1 帧，最多 2 对在途；平衡模式分别为 2 帧和 3 对。
- 已完成结果按整对输出的数量限制缓冲，保留中间插帧的播放间距。过载后丢弃旧输入，断流恢复不补算大段历史画面。
- 实时补帧使用独立播放锚点，避免普通回放的 150–600ms 迟到容差与时钟回拨累积延迟。
- 固定目标网格复用上一对已输出的源帧，避免再次执行 NV12 往返转换；源帧和插值帧仍保持一致的色彩处理。
- 显示采用双 drawable、非阻塞 GPU 在途上限和屏幕刷新率拉帧；GPU 完成前保留源像素缓冲和 CVMetalTexture 引用。
- 固定目标帧率始终按目标时间网格输出；修复原生 60→60 被当成 2X、30→120 被当成 2X 的问题。网格末端拷贝当前帧，避免多延迟一个源帧。
- 性能面板新增「应用内画面滞后」及采集、AI 输入、在途任务读数。该估计截止到显示取帧，不含 HDMI/USB、采集卡内部处理、GPU 展示和屏幕扫描。

## 模型比较

设备为 Apple M1 Pro。用户停止游戏后重新测量，20 次预热后样本，每次合成一张中间帧；仅作本机当前运行方式的比较。

| 方案 | 输入与推理条件 | 均值 | P95 |
|---|---|---:|---:|
| 现有 RIFE 4.25 Lite | 1080p NV12 源，576p 光流，单实例完整 `runChain` | 44.58 ms | 46.72 ms |
| 现有 RIFE 4.25 | 同上 | 44.05 ms | 47.69 ms |
| 现有 RIFE 4.26 | 同上 | 42.39 ms | 46.89 ms |
| Apple Low Latency Frame Interpolation | 720p NV12 源，单张中间帧 | 5.53 ms | 5.58 ms |
| Apple Low Latency Frame Interpolation | 1080p NV12 源，单张中间帧 | 113.57 ms | 116.45 ms |

这些值不包含采集与显示，也不是同分辨率、同画质的跨模型排名。RIFE 数据使用现有生产推理代码、六张循环移动图案输入；Apple 数据使用合成移动图案。实际游戏的质量、运动伪影和持续负载需要另外检查。

第一轮中 Lite 没有显示速度优势，故未自动替换现有模型。当时 Apple 接口通过支持检测，720p 值得继续评估，1080p 实测不适合低延迟。第二轮已接入下述 720p 中间帧方案。该低延迟配置需要 macOS 26 或更高版本，并应做运行时支持检测和后台预热。

来源：[Practical-RIFE 官方模型说明](https://github.com/hzwer/Practical-RIFE#trained-model)、[Apple 实时视频效果介绍](https://developer.apple.com/videos/play/wwdc2025/300/)、[Apple 低延迟插帧配置](https://developer.apple.com/documentation/videotoolbox/vtlowlatencyframeinterpolationconfiguration)。

## 第二轮：Apple 低延迟模式与 Macrife 参考

用户选择优先帧率与跟手感，接受 AI 中间帧细节可能偏软。模型配置面板新增 **Apple 低延迟 (720p AI · 原帧保真)**，用于 2X 插帧：

- 原始 1080p 帧直接保留，同一 CVPixelBuffer 原样输出；中间帧在最多 1280×720 生成后恢复源尺寸。
- NV12 两平面在 Metal 直接缩放。缩小、`VTFrameProcessor.process(with:parameters:)` 和放大合入一个 command buffer，只等待一次；缓冲与 CVMetalTexture 引用一直保留至 GPU 完成。
- 以最新采集时轴和实际处理均耗安排显示，消除启动预热留下的固定延迟。第一张 AI 帧也建立正确锚点，避免被原帧的零等待时钟直接吞掉。
- 120Hz 显示循环继续及时取帧；没有新画面时保留上一张 drawable，避免重复绘制旧画面。窗口缩放与设置变动仍触发重绘。
- 非 2X 帧率、HDR 或不支持的系统/格式回退现有 RIFE。Apple 不适用的 RIFE 调度控件在面板中禁用，状态区显示真实后端。
- 延迟增加最近 240 张显示取帧样本的 P50/P95；FPS 使用约一秒计数窗口和单调时钟，避免额外诊断刷新把 60fps 读成 40/70fps。

### 实测

| 已显示帧 | 1473 |
| 真正生成的 AI 中间帧 | 751 |
| 最近 240 帧应用内滞后 P50 | 35.3 ms |
| 最近 240 帧应用内滞后 P95 | 41.9 ms |
| 最后诊断时刻的应用内滞后 | 33.5 ms |

### 参考 Macrife

找到的工程是本机 `Dev/Macrife`。参考 `Sources/Macrife/Pipeline/RIFEEngine.swift` 的双帧 `preparePair` / `makeRGBInputs(from:and:)`：播放器现有 RIFE 也把两个输入的转换合并提交，并在 GPU 完成前保留纹理引用。没有直接采用离线转码的大在途窗口。

相同输入下，合并前后输出的 **3,110,400 个 NV12 有效字节完全一致**（MAE=0、最大误差=0）。该改动的单实例提速很小，主要收益来自 Apple 模式与实时播放调度，不能把离线吞吐量当作采集延迟。

## 第三轮：手动主机30FPS／60FPS采集

按用户最终要求取消自动识别，采集配置第5项改为「主机30FPS模式」，仅保留两个选项：

- **原始输入（不抽帧）**：按实际采集帧率路由。
- **主机30FPS（60FPS采集 · AI补到60FPS）**：保持设备60FPS，立即从第一张输入开始固定隔帧取样，不做图像比较、检测预热或重复帧确认。启动时选择设备真实上报的60Hz档位，AI目标设为60FPS；macOS26及以上选择Apple低延迟后端，失败仍走既有RIFE回退。

取样使用采集PTS相对于首帧的奇偶网格，漏一个回调不会反转取样相位。重复槽位在进入待处理队列前丢弃，不会在GPU繁忙时把较早一拍的原帧替换为同一画面的晚一拍。该模式由用户保证主机运行于30FPS/60Hz的2:2输出；主机变成60FPS时应手动切回原始输入。固定相位不判断哪张图像是重复，因此不声称每次启动都选中HDMI重复对中较早的一张。

内容帧率随每个排队输入传到处理线程，避免切换模式时使用另一张帧的节奏。切换和断流只清除系统AI的上一帧引用，保留已预热模型及计数。

- `sh Tests/run-apple-interpolation-tests.sh`：真实系统AI收到1080p60的A,A,B,B合成输入，35张源帧加34张AI帧按1/60秒连续输出，原始像素缓冲保持对象一致；清理帧对历史后不会跨模式插值。独立全链路均耗6.88ms、P95 7.73ms，仅代表此次独立合成测试。

## 静止文字闪烁修复

原始1080p与720p生成后放大的中间帧交替显示时，小字/细线清晰度变化会造成闪烁。在实际系统AI合成的静止单像素笔画样本中复现，修复前亮度MAE为30.777/255。

在原有Metal放大阶段融合静止区域保护：比较相邻两张1080p原帧的3×3邻域亮度和色度，仅在一致区域复用当前原帧的全分辨率像素，变化区域继续保留AI结果，阈值附近平滑混合。沿用同一个command buffer及一次GPU等待，不增加帧缓冲；原始帧对象保持不变。NV12视频/全范围分别处理，合成输出均保持限制范围，避免黑位或彩色文字的范围切换。打包422回退仍使用原来的普通缩放路径，当前采集卡默认NV12走完整保护。

真实AI测试新增静止细字、彩色高频细线、全范围转换，以及运动区域不能被整帧复制替代的检查。限制范围静止细字MAE为0.000/255，全范围转换后为0.449/255（8位量化）；彩色像素误差不超过1。运动区域仍与当前原帧明显不同，AI输出数量、时间戳与1080p原帧保真回归均通过。


## 第二次文字修复：透明HUD上的位移/重影

用户反馈第一版仍然左右抖动、重影。第一版的合成用例覆盖完全静止的文字，未覆盖游戏HUD背景和抗锯齿变化。读取USB3 Video的16张实际游戏帧（约0.5秒，保持原规格），对比原始帧与真实AI输出，任务、道具和操作提示文字在原帧位置稳定，在AI帧中发生明显形变。3×3邻域中的背景像素变化会让原有静止保护失效。

新增屏幕边缘HUD的笔画/轮廓保护：

- 在相邻1080p原帧中匹配同位置的亮/暗细笔画，不再要求笔画旁的背景全部静止。
- 半分辨率遮罩覆盖每个2×2原像素，并向外扩展约6像素，保护抗锯齿、阴影及AI偏移产生的重影。
- 遮罩短暂衰减，避免保护随噪声每帧开关；复用的是当前原帧，不冻结旧文字。
- 中央视野继续AI运动插值；中心静止画面仍沿用原有静止像素保护。该增强主要针对屏幕边缘HUD，不保证消除中心移动姓名牌等所有模型伪影。
- 缩小、AI、遮罩和放大仍在同一个command buffer中执行，一次等待，不增加源帧前视或帧队列。换模式和断流清除遮罩历史。
- 原生路径实际启用后，处理状态新增“HUD文字保护”；打包422回退不显示该标记。

真实游戏15对原帧/中间帧对照，统计位置稳定的亮文字像素，亮度MAE（8位）：

| 区域 | 第一版保护 | 新保护 | 像素样本数 |
|---|---:|---:|---:|
| 任务文字 | 36.911 | 0.000 | 18216 |
| 操作提示 | 51.554 | 0.000 | 1678 |
| 道具文字 | 31.610 | 0.000 | 12466 |

这是这段游戏样本的像素验证，不代表所有字体、透明度和运动条件。原始游戏帧及对照仅保存在本机临时目录，没有加入仓库。

新增程序生成的“固定细字＋移动背景＋变化抗锯齿”回归，笔画误差0.517/255，原始帧保真、运动区域保持AI、全/限制范围和彩色细字回归通过；采集时序16项回归通过。

最终预览已确认显示“HUD文字保护”。用户在验证时切回固定60FPS，并开启MetalFX空间上采样；当次UI采样为59.0FPS，处理均耗18.9ms，最近240张显示取帧P50 38.7ms / P95 43.6ms，输入与AI待处理队列为空。这是运行时快照，启动后曾关闭AI，因此不把全程平均读数当作AI路径的持续帧率。新的主观观看效果仍以用户实际游戏反馈为准。

## 纯画面低延迟补帧候选（2026-11-16，仅调研）

目标是处理普通采集卡的前后两帧，不要求游戏提供深度、运动向量或相机参数。允许模型从画面内部估计光流。以下只核对公开文档、代码和权重入口，没有下载新模型、安装依赖、编译、测试或更改当前后端。

### 现有可用基线

当前 Apple VideoToolbox 低延迟接口也属于纯画面路线：参数包含 sourceFrame、previousFrame、interpolationPhase 和 destinationFrames，不需要外部运动纹理或深度。它是系统管理模型，不能作为可独立导出权重的开源模型；macOS26+ 且运行时支持时可用。现有 720p 路径已有前文所列本机短测，仍应作为对照。

来源：[Apple 低延迟参数接口](https://developer.apple.com/documentation/videotoolbox/vtlowlatencyframeinterpolationparameters)。

### 选择原则

按当前项目的**可接入性**，先看 RifeMetal fast，再看 ODF-VFI；按**新轻量网络探索**，先看 Nano，再看 IFRNet-S。这些不是已证实的本机速度排名。项目第一轮实测中 4.25 Lite 未快于现有 4.26，不能仅凭 Lite 名称替换。

纯两帧插值仍要等待后一张真实帧；30FPS 内容的相邻帧间隔约 33.3ms。模型耗时、采集/显示等待和排队延迟应分开记录，不能把模型 FPS 当成输入到屏幕总延迟。恢复实测时，应统一源内容、输出尺寸与内部推理档位，比较预热后处理 P50/P95、显示 FPS、应用内滞后，以及 HUD/遮挡/快速运动质量。

## 设置分层调整（2026-11-16，仅静态验证）

用户要求将低延迟、补帧后端/模型、光流推理分辨率和数值精度解耦；不具备精度调节能力的模型隐藏精度选择。本轮只修改代码、进行纯配置/队列检查、Release构建和静态配置面板截图，没有开启采集、运行模型或做性能实测。

### 当前分层

1. **输出模式**：倍率或目标FPS。
2. **补帧后端**：RIFE（Core ML）／Apple系统补帧（VideoToolbox）。
3. **模型权重**：RIFE v4.26／Heavy；Apple显示系统管理模型，后端不再混入RIFE权重列表。
4. **光流推理分辨率**：独立配置，分别按RIFE权重型号、Apple后端保存，切换后恢复该配置。
5. **数值精度**：仅在当前模型有至少两种实际可用精度时展示下拉。当前RIFE包只有FP16，Apple不公开FP16/FP32控制，因此两者均隐藏精度下拉，显示只读能力说明。
6. **采集延迟策略**：极限／平衡／标准，独立于后端、模型、推理分辨率。手动主机30模式仍设定60FPS采集与输出目标，但不再自动替换用户选择的补帧后端。
7. **画质增强**：MetalFX空间超分、Anime4K仍是独立渲染阶段。

### 分辨率实际接线

| 后端/模型 | 配置档 | 实际处理方式 |
|---|---|---|
| RIFE v4.26 | 576p／720p／1080p／1440p | 选择已安装的相应CoreML模型目录，不再仅改变一个未使用的UI缩放值。 |
| RIFE Heavy | 576p／720p／1080p | 没有1440p包，不显示该档；现有执行器对Heavy的16通道特征仍有兼容限制，回退常规RIFE时保留相同分辨率，并报告实际模型。 |
| Apple系统补帧 | 576p／720p／1080p／1440p上限 | 等比适配源尺寸、不放大源图；尺寸加入会话配置键，修改后重建处理配置。具体尺寸由系统运行时检查，不支持时走原有RIFE回退。 |

RIFE的720p包使用1280×768模型画布，1080p包为1920×1088，1440p包为2560×1472；状态显示实际画布尺寸。Apple请求上限高于源分辨率时保持源尺寸。新增/高分辨率档只完成配置与模型元数据检查，未运行推理验证或评估实时吞吐。

- `sh Tests/run-interpolation-settings-tests.sh`：7组纯配置检查，覆盖迁移、分模型保存、持久化、延迟解耦、能力范围、模型目录映射及推理尺寸几何；不创建GPU/模型会话。

### MetalFX 采集补帧实验性接入（2026-11-16，未做视频实测）

新增独立的 `MetalFX 补帧（实验性）` 后端，实际调用 `MTLFXFrameInterpolator`，与渲染阶段的 MetalFX 空间超分开关独立。支持 SDR 2X，保留源帧对象与分辨率，中间帧按所选 576p / 720p / 1080p / 1440p 上限处理后恢复源尺寸。分辨率单独保存在 `macrife.interpolation.metalfx.flowResolution`；数值精度由系统管理，不显示精度选择框。

采集卡没有游戏引擎运动矢量、深度、相机参数，也不能分离已经合成的 UI。此桥接方案用 Vision `VNGenerateOpticalFlowRequest` revision 1 / low 估算当前到上一帧的像素运动，关闭 raw network output；深度固定为 0.5，近远平面 0.1 / 100、视角 60°、jitter 0 均为近似。它不等价于游戏内完整 MetalFX 集成，不能据此承诺更低延迟或修复重影。Vision 的 RG32Float 光流存储格式不代表可以调整 MetalFX 内部模型的数值精度。

处理顺序为 NV12 缩小和 RGB 转换 → Vision 光流估算 → MetalFX 补帧 → NV12 与原分辨率恢复。已有的静止 HUD 笔画保护复用在 NV12 输出阶段；打包 YUY2 可通过 VideoToolbox 转换参与补帧，但不宣称该路径具备 HUD 保护。Vision 与 MetalFX 之间需要同步，额外光流、色彩转换和拷贝均可能抵消补帧器自身的速度优势。

运行时通过 `supportsDevice` 检查设备；macOS 版本、帧率、HDR、格式、光流或 Metal 处理失败时返回 RIFE 路径，并显示回退原因。格式/尺寸切换重建会话；停止、重载、跳转、采集节奏改变和帧间隙清除旧帧或历史，避免跨时间段配对。未验证设备实际支持情况、Vision 运动方向/坐标、MetalFX 首次历史行为、输出画质、帧率或延迟。

已通过：Release 构建、应用签名验证、8 组配置检查、16 项采集队列/时钟回归检查、两个新色彩转换内核的 Metal 编译。静态设置 PNG `/private/tmp/macrife-settings-metalfx.png` 确认新入口与精度隐藏。没有运行采集、光流请求、模型或 MetalFX 插帧。已打开的旧应用进程须退出并重新打开工作区根目录的新 `.app` 才会加载新代码。

接口依据：本机 macOS 27.2 SDK 的 `MTLFXFrameInterpolator.h`、`VNGenerateOpticalFlowRequest.h`；[MetalFX 插帧输入与 UI 要求](https://developer.apple.com/videos/play/wwdc2025/211/)、[Vision 光流请求](https://developer.apple.com/documentation/vision/vngenerateopticalflowrequest)。
